# Claude Code 指示書：フック検出器群の実装とトリガー並走基盤

対象プロジェクト: `Delta_Engine_Pro4web`（branch: ui-refresh-v2）
前提資料: `hook_trigger_catalog_v1.md`（フック約90種・代表トリガー50型のカタログ）を必ず先に読むこと。本指示書はカタログのフックID・型IDを参照する。

## ■ 背景と方針決定

- Step 2集計により、flow_response単独シグナルは新旧期間で成績の再現性なし（一致率相関 -0.025）と判明
- 原因分析：現行の自動判断は約定データ派生の単一軸であり、板（DOM）という独立情報源が判断に使われていない
- お館様の決定：**DOM検出器群を先に実装し、型を揃えてから一斉にobserve並走させる**。弱い型を先行稼働させる案は棄却

## ■ 実装スコープ

### 1. DOM系フック検出器（A01〜A24、最優先）

OrderBookStateManagerの板状態（100ms差分）の上に検出層を新設する。カタログA表の24フックすべてを対象とするが、実装困難なものは理由付きでスキップ可（要報告）。

特に重要（多くの型の解禁に直結）：
- A01/A02 大口壁の出現
- A03/A04 壁のpull（約定を受けずに消滅）
- A05〜A08 板の急薄化・急増強
- A09/A10 板の非対称
- A17/A18 アイスバーグ疑い
- A21/A22 板の空洞化

### 2. 板×約定関係の拡張（C03〜C09）

既存AbsorptionDetectorを拡張または並設し、吸収失敗（食い破り）、吸収の反復、壁への衝突開始→完食/防衛の判定を追加する。

### 3. 清算系検出器（E01〜E06）

forceOrderストリーム（既にバッファ取得済み）に検出層を新設。単発大口・連鎖・無反応（吸収された清算）・枯渇。

### 4. OI系検出器（F01〜F05）

open_interest_samples（既存14,053件の取得経路）に検出層を新設。OI変化×価格方向の4象限＋急変。

### 5. 価格構造フック（G01〜G11、フィルター用）

直近高安・ブレイク・ブレイク失敗・VWAP・レンジ端。既存candlesから算出。Volume Profile系（G09）が重い場合は後回し可（要報告)。

### 6. flow_response拡張（D06〜D08）

状態の急転換検出と多窓一致判定。既存stateの派生なので軽微。

## ■ 閾値の決定方法（全検出器共通・必須）

勘で決めない。以下の手順を踏む。

1. **実測分布から初期値を算出** — 既存記録（trades 885k件、板記録、OI 14k件等）から各量の分布を取り、閾値はパーセンタイル基準で初期化する（例：大口＝約定サイズ上位1%点）。どのフックにどの分位を使ったか、根拠を一覧で報告する
2. **全閾値を設定ファイル化** — ハードコード禁止
3. **リプレイで発火頻度を確認** — 決定論リプレイで過去数日分を流し、各フックの発火回数/日を集計して報告する。ノイズ級（多すぎ）と沈黙級（少なすぎ）を特定し、調整案を提案する

## ■ トリガー並走基盤

1. **型（playbook）を宣言的に定義できる仕組み** — カタログ第3部の「主フック＋確認フック＋否定フック＋文脈フィルター＋方向」を設定ファイルで記述でき、コード変更なしに型の追加・変更ができる構造にする
2. **初期搭載する型** — カタログT01〜T50のうち、実装済みフックで構成可能な全型。搭載できた型/できなかった型（不足フック付き）の一覧を報告する
3. **共通記録フォーマット** — 発火ごとに：型ID・全根拠フックの値とタイムスタンプ・発火時Binanceミッド・HFM bid/ask/spread・モード。parquet永続化
4. **ニアミス記録** — 主フック成立＋確認不成立で見送ったケースも記録（型別）
5. **outcome接続** — 全発火を既存outcome trackerに乗せ、horizon 60/180/300/600秒のforward_return_bps / MFE / MAEを記録
6. **モード** — 全型observe固定で開始。発注コードへの接続は実装するが、live化はお館様の明示的指示があるまで封印

## ■ 実装制約

- 既存の検出器・パイプライン・ストレージ・WebApp・稼働中システムの動作を変更しない。検出層・トリガー層は独立モジュールとして追加
- 記録の改変・削除は一切しない
- パフォーマンス：100ms板差分処理に検出層を載せても遅延が問題化しないよう、重い計算は非同期化。処理遅延の計測値を報告に含める

## ■ 進め方（各段階でお館様の確認を取る）

1. **設計提案** — モジュール構成（ファイル名・配置・接続点）、実装順序、閾値の分位対応表 → お館様OK後に着手
2. **検出器実装＋リプレイ発火頻度報告** → お館様確認
3. **トリガー並走基盤実装＋搭載型一覧報告** → お館様確認
4. **observe起動手順の報告** → お館様が起動
5. **数日稼働後、型別成績の一次集計**（Step 2と同一手法）→ 型の選抜・閾値較正へ

一気に全部やらない。段階ごとに止まって報告すること。
