率直に言う。これは「かなり優秀な観測画面」だが、現状は情報を増やすより、時間軸の統一と通知整理が必要だ。執行判断まで完結する画面としては、まだ不足がある。

- 30秒・1分・3分は買い圧力＋価格上昇
- しかし20本CVD傾斜はマイナス
- OIも減少
- 5分以上のFlowは未確定
- Relative Volume、Absorption、Imbalanceも確認できない

良い点は明確だ。

- Price・CVD・Delta・OI・Footprintを独立して読める
- 30秒～30分のFlowを同時比較できる
- 選択足の詳細とライブ値が分かれている
- FootprintとTime & Salesを同時確認できる
- 単一の怪しい総合スコアへ潰していない

一方、過剰なのは通知だ。SELL TAPEがTime & Sales、Flow Events、Alerts、右下トーストに重複し、しかも0.89～1.00が連発している。これでは「異常」ではなく「通常の売り約定」を何度も警報している状態になる。開始時に1回通知し、その後は件数・最大強度・継続時間へ集約した方が実戦的だ。トーストも同時に1個で十分。

最も危険なのは時刻表示だ。画面上部とTime & Salesは`04:20 JST`なのに、Flow EventsとAlertsは`19:20`になっている。同じ瞬間のUTC表示だとしても、タイムゾーン表記なしの混在は検証ミスを起こす。ここは最優先で統一すべきだ。

不足しているものは次の4点。

1. Resting liquidity  
   現在板、bid/askの補充・取消、壁の移動が見えない。今の売りが「売り手が強い」のか「買い板へ吸収されている」のかをFootprintだけでは確定できない。DOMまたは時間×価格Heatmapが最重要。

2. データ鮮度  
   `HFM STALE`や欠測は出ているが、各データの最終受信から何ms経過したかが欲しい。上部の`LATENCY 0ms`だけでは、trade・book・OIのどれが新鮮なのか判断できない。

3. 市場構造の基準線  
   Session VWAPはあるがPARTIAL。加えて、Session Open、高安、前日高安、Volume ProfileのPOC・VAH・VALから、必要なものだけ欲しい。注文フローが「どこで」発生したかが重要だからだ。

4. 執行・リスク情報  
   実際に発注する画面なら、現在ポジション、平均価格、予定ストップ、手数料込み損益、spread、最大損失が不足している。観測専用なら不要だが、売買完結画面なら必須。

総評は、センサーの種類は十分。これ以上インジケーターを増やす必要はない。優先順位は、

**時刻統一 → TAPE通知集約 → DOM/Heatmap → データ鮮度 → 最小限の市場構造・リスク表示**

だ。この画面の最大の弱点は情報不足そのものではなく、重要度の低いSELL TAPEが重要情報を圧倒していることだ。

厳密な視線順序はこうです。

1. データ状態を0.5秒確認  
   `LIVE / SYNCED / Trade age / OI age / gapなし`を確認します。古い画面では一切判断しません。

2. Heatmap＋現在価格  
   現値の上下、およそ直近10～20 ticksを見ます。

   - 大きなbid／askはどこか
   - 接近すると板が逃げるか、残るか
   - 約定されても補充されるか
   - 一気に食われるか
   - 食われた後、その価格帯を抜けて定着するか
   - 厚い板の手前で価格が止められているか

   重要なのは、表示数量ではなく、**持続・約定・補充・価格反応**です。

3. 価格の大きな位置  
   Session VWAP、Session High/Low、前日高安、POC・VAH・VALとの位置を確認します。

   同じ買い吸収でも、VWAP下と前日安値では意味が違います。  
   私は必ず「何が起きているか」より先に「どこで起きているか」を確認します。

4. Flow Response  
   基本は、

   **5分で異変 → 1分で始点 → 15分で背景**

   の順です。

   - 圧力に価格が追随している
   - 圧力があるのに価格が止まる
   - 圧力と逆方向へ価格が動く

   ここで初めて、Heatmap上の反応が単発か継続現象かを確認します。30秒と3分はタイミング補助です。

5. PRICE → CVD → Delta  
   次に3段チャートを見ます。

   - 売りDeltaなのに価格が下がらない
   - CVDが下がっているのに価格が安値を更新しない
   - 買いDeltaなのに価格が上がらない
   - CVDだけが伸びて価格が止まっている

   Heatmapの壁と、この価格反応が一致したときに意味が強くなります。

6. Footprint  
   エントリー候補の価格帯だけを精査します。

   - どの価格で成行注文が集中したか
   - aggressive flowが価格を動かせたか
   - 反対側に吸収されたか
   - stacked imbalanceが継続したか
   - POCが進行方向へ移動したか
   - 突破後に出来高を伴って受け入れられたか

   Footprint全体を眺めるのではなく、Heatmapで絞った価格帯を確認します。

7. OI  
   OIは方向ではなく、動きの正体を判別するために見ます。

   - 価格↑・OI↑：新規ポジションを伴う上昇候補
   - 価格↑・OI↓：ショートカバー候補
   - 価格↓・OI↑：新規ショート候補
   - 価格↓・OI↓：ロング清算・手仕舞い候補

8. Time & Sales  
   最後の発火確認に使います。Tapeから相場観を作り始めません。

   - 大口約定が連続したか
   - 同じ価格で吸収されたか
   - 約定速度が急増したか
   - sweep後に価格が進んだか
   - 反対売買がすぐ現れたか

   Alertsは補助であり、私の最初の視線には入りません。

私のロング条件を一例で表すと、

> 重要な価格帯へ下落  
> → 売りがbidへ大量にぶつかる  
> → bidが補充される  
> → Delta/CVDは下がるが価格は下がらない  
> → ask側の流動性が薄くなる、または食われる  
> → Footprintで買いが価格を一段上へ動かす  
> → 押し戻されても突破価格を維持

この順序を確認してから入ります。

つまり、最初に見るのは「BUYかSELLか」ではありません。

**現値がどこにいて、直近の流動性へ当たったとき、成行注文に対して価格がどう反応しているか。**

ここが私の出発点です。

可能です。むしろ1～5は、DeltaEngineのHook／Predicate／Episode構造と非常に相性がよいです。

ただし、5項目を同格の「売買フック」にしてはいけません。役割を分けます。

| 項目 | 自動化上の役割 | 例 |
|---|---|---|
| 1. データ状態 | Hard Gate／Invalidation | FEED_STALE、SYNC_LOST、RECOVERED |
| 2. Heatmap＋現値 | Liquidity Event Hook | WALL_RELOAD、PULL、CONSUMED、FAILED_SWEEP |
| 3. 重要価格位置 | Location／Context Hook | NEAR_VWAP、TOUCH_PDH、RECLAIM_VAH |
| 4. Flow Response | Temporal State Hook | 5M_STALLED、1M_TRAPPED、15M_BACKGROUND |
| 5. Price→CVD→Delta | Confirmation／Contradiction Hook | SELL_ABSORPTION、BUY_TRAPPED、DIVERGENCE_RESOLVED |

重要なのは、Hookが売買判断を確定するのではなく、**該当Situationの再評価を起動する装置**になることです。

## 1. データ状態

これは市場状況ではなく、全Situationの入口に置く安全ゲートです。

主なHook:

- `TRADE_FEED_STALE`
- `ANALYSIS_STALE`
- `OI_STALE`
- `STREAM_GAP`
- `CLOCK_SKEW`
- `FEED_RECOVERED`
- `HISTORY_WARMUP_COMPLETE`

データ異常時はSituationを進めず、途中のEpisodeも無効化または一時停止します。

`RECOVERED`後も、異常前の古いHeatmap状態やFlow状態をそのまま継続してはいけません。必要な観測窓が再完成するまでfail closedです。

## 2. Heatmap＋現値

Heatmapの描画画像を解析するのではなく、元の板frameと約定からHookを生成します。

主な原子Hook:

- `PRICE_APPROACHING_LIQUIDITY`
- `LIQUIDITY_PERSISTING`
- `LIQUIDITY_RELOADING`
- `LIQUIDITY_PULLING`
- `LIQUIDITY_MIGRATING`
- `LIQUIDITY_CONSUMED`
- `SWEEP_STARTED`
- `SWEEP_COMPLETED`
- `SWEEP_FAILED`
- `PRICE_ACCEPTED_BEYOND_LEVEL`
- `PRICE_REJECTED_FROM_LEVEL`
- `LIQUIDITY_VACUUM_FORMED`

最も価値があるのは壁の大きさそのものではなく、

> 接近 → 約定 → 補充／取消 → 突破／反発

という時間順序です。

表示されただけの壁はspoofの可能性があります。一定時間残ったか、実際に約定されたか、約定後に補充されたかを別々に記録する必要があります。

## 3. 重要価格位置

これはSituationを探し始める場所を限定するLocation Hookです。

対象候補:

- Session VWAP
- Session Open
- Session High／Low
- Previous Day High／Low
- POC
- VAH／VAL
- Range High／Low
- 記録済みの重要反応価格

各levelに対して、

- `APPROACH`
- `TOUCH`
- `CROSS`
- `HOLD_ABOVE`
- `HOLD_BELOW`
- `RECLAIM`
- `REJECT`
- `ACCEPT`

を分離します。

単に「PDHへ到達」だけでは弱いです。

> PDH接近  
> → ask liquidityへ買いがぶつかる  
> → askが補充される  
> → CVDとDeltaは上がる  
> → 価格はPDHを越えられない

まで進んだとき、初めて意味のあるSituationになります。

## 4. Flow Response

Flowは単発値より状態遷移をHookにします。

例えばBUY側なら、

- `BUY_PRESSURE_STARTED`
- `BUY_EFFECTIVE_ENTERED`
- `BUY_STALLED_ENTERED`
- `BUY_STALLED_PERSISTED`
- `BUY_TRAPPED_ENTERED`
- `BUY_TRAPPED_RESOLVED`
- `BUY_PRESSURE_ENDED`

SELL側も対称です。

時間窓は独立票として数えません。同じ約定を含んでいるからです。

役割は次のように分けるのがよいです。

- 5分: Situationをarmする主観測
- 1分: 現象の始点と遷移を検出
- 15分: 広い背景を付与
- 30秒: 早期wake
- 3分: 1分と5分の橋渡し
- 30分: regime context

例えば5分と1分が同じBUYだから「2票」とはしません。

`5M_BUY_STALLED → 1M_BUY_TRAPPED → 15M_SELL_BACKGROUND`

という順序付きの観測事実として保持します。

## 5. Price→CVD→Delta

既存の8パターンを、表示名だけでなく状態遷移として利用できます。

原子Predicateの例:

- Price direction
- CVD direction
- Delta sign
- Price change magnitude
- CVD change magnitude
- Delta impulse magnitude
- divergence onset
- divergence persistence
- divergence resolution
- price failure to progress

特に重要なのは次です。

- 売りDelta＋CVD低下、価格は下がらない
- 買いDelta＋CVD上昇、価格は上がらない
- CVDは安値更新、価格は安値を更新しない
- 価格は高値更新、CVDは高値を更新しない
- divergence後に価格がどちらへ解放されたか

「方向」だけでなく、変化量、継続時間、価格進行の失敗を分離すると、かなり多くの状況が見えてきます。

## 洗い出せるSituation

最初に有望なのは、次のようなSituationです。

### 1. Seller Absorption Reversal

- 重要supportへ接近
- bid liquidityが持続
- 売りがbidへ約定
- bidが補充
- CVD／Deltaは下向き
- 価格は下がらない
- SELL FlowがSTALLEDまたはTRAPPED
- その後askが消費され、価格が上へ解放

売り手が攻撃しているのに下げられないSituationです。

### 2. Buyer Absorption Reversal

上記の上下反転です。

- resistance
- askの持続・補充
- 買いCVD／Delta
- 価格が上がらない
- BUY STALLED／TRAPPED
- 下方向へ解放

### 3. Breakout Acceptance

- 重要levelへ接近
- 反対側liquidityが消費またはpull
- aggressive flowが継続
- Price／CVD／Deltaが同方向
- level突破後も価格が戻らない
- levelの反対側に新しいliquidityが形成
- FlowがEFFECTIVEを維持

単に一度越えただけではなく、突破価格の外側で受け入れられた状態です。

### 4. Failed Breakout／Trap

- levelを一度突破
- 大量のaggressive flow
- CVD／Deltaは突破方向
- 価格進行が停止
- liquidityが再補充
- priceがlevel内側へ戻る
- FlowがSTALLEDからTRAPPEDへ遷移

典型的なbull trap／bear trap候補です。

### 5. Liquidity Vacuum Acceleration

- 進行方向のliquidityが連続してpull
- 反対側からのaggressive flowが継続
- Price／CVD／Deltaが同方向
- FlowがEFFECTIVE
- 直近levelを短時間で通過

薄い方向へ価格が走るSituationです。壁の突破とは別に扱うべきです。

### 6. Pressure Without Progress

- aggressive flowが一定以上継続
- CVDとDeltaは明確
- 価格進行が小さい
- Heatmap上で反対側liquidityが補充
- FlowがSTALLEDを継続

まだ反転確定ではありません。吸収、蓄積、分配の候補状態です。

### 7. Range Rotation／No Trade

- Value Area内部
- 上下に近いliquidity
- Flowの方向が短時間で交代
- CVDと価格に持続性なし
- 突破してもすぐ戻る

これも重要なSituationです。「取引しない状態」を明示的に洗い出せます。

## 実装構造

私なら4層に分けます。

```text
データ正常性Gate
    ↓
原子Hook
    ↓
Observation Predicate
    ↓
順序付きSituation State Machine
    ↓
事後結果の保存
```

例:

```text
DATA_HEALTHY
→ NEAR_PDH
→ ASK_WALL_PERSISTING
→ BUY_AGGRESSION
→ ASK_RELOADING
→ PRICE_FAILED_TO_PROGRESS
→ BUY_FLOW_STALLED
→ PRICE_RETURNED_BELOW_PDH
= FAILED_BREAKOUT_SHORT_CANDIDATE
```

この最後も発注ではありません。

発生時刻から1分、3分、5分、10分後のreturn、MFE、MAEを保存し、どのSituationが本当に有効かを検証します。

## 最大の注意点

自動化は可能ですが、単純な全組み合わせ生成は危険です。

5分類の条件を機械的に掛け合わせると、数百～数千の意味の薄いSituationが生まれます。防ぐ条件は次です。

- Hookはwake-upであり成立断定ではない
- 同じsource eventを複数stateの順次成立証拠に再利用しない
- 1分・5分・15分を独立票として数えない
- source timestampとfreshnessを必須にする
- book gap後はHeatmap系Predicateをreset
- 順序が逆なら不成立
- timeoutを持たせる
- 途中で反証されたらinvalidate
- threshold未較正はUNVALIDATEDのまま
- 発注へ直接接続しない
- 成立例だけでなく、不成立例とnegative sampleも保存する

結論として、**1～5の自動化は可能であり、複数の実戦Situationを洗い出す最も正しい方向**です。

ただし成果物は「BUY／SELL Hook」ではなく、

**データ正常性＋位置＋流動性変化＋Flow遷移＋Price/CVD/Delta反応から構成される、順序付きSituation候補**

にするべきです。これならDeltaEngineの独立観測思想を壊さず、人間が見落とす短時間の組み合わせを機械に拾わせられます。
