## 3. タスクA: 記録物の現物提出

対象: `data_05M/depth_history_raw/symbol=BTCUSDT/` 配下(Phase 1 P1-2/P1-3 で記録した現物)。

報告する項目:

1. セグメントファイルの一覧(ファイル名・byte数・行数)。
2. manifest の全文(現物をそのまま貼付)。
3. 最初のセグメントの先頭5行と末尾5行(現物をそのまま貼付)。
4. `e:"depthSnapshot"` 行の総数と、各出現位置(セグメント名:行番号)。`_capture_reason` の値も併記。
5. セグメントが複数ある場合、ローテーション境界の前後各2行(現物)。
6. 全行走査での float 型混入チェック結果(数値がJSON number型で入っている行数。0件を期待)。

## 4. タスクB: 連続性の機械検証

検証スクリプトを作成し(保存先は §1)、以下を機械的に検証して結果を報告する。

1. **depthUpdate 連続性**: 全隣接ペアで `pu(後) == u(前)` が成立するか。不成立の件数と、不成立箇所すべての(セグメント名:行番号、前行の u、後行の pu)。
2. **snapshot 接続**: 各 depthSnapshot(`u` = lastUpdateId)について、直後の depthUpdate が `U <= u_snapshot + 1 <= u` を満たすか。各 snapshot ごとの判定結果。
3. **セグメント跨ぎ**: ローテーション境界を跨ぐ隣接ペアでも 1 が成立するか(境界が存在する場合のみ)。
4. 検証スクリプトの実行コマンドと出力全文を報告書に貼付。

判定基準は報告のみでよい。不成立があっても修正・再記録はしない(統括が対処を決める)。
