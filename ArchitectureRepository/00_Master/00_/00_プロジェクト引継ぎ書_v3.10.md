# 3. 恒久運用ルール(v3.9 以降で確立、要遵守)

## 3.1 Code 完了報告時の三点セット

Code は完了時に以下を必ず実施:

1. **`ArchitectureRepository/00_Master/CompletionLog.md`** に完了エントリを追記(末尾追記、時系列)
2. プロジェクト全体を `DeltaEngine_<指示書ID>_完了.zip` で ZIP 化。`__pycache__` / `.pytest_cache` / `data/parquet` / `data/duckdb` は除外可、それ以外(`ArchitectureRepository/` と `project/`)は全て含む
3. チャット完了報告文と ZIP の両方を提出

**注意**: B-1 完了時点では CompletionLog.md がまだ未作成。B-2 完了時に B-1 分を後追い追記する指示を B-2 に含めている。

## 3.2 web による検証(Code 申告を裏取り)

Code 完了報告のたびに、お館様が web に ZIP を渡す。web は以下を実施:

- 指示書と ZIP の逐語照合(追加内容の逐語一致、無変更宣言ファイルの前回 ZIP との diff)
- pytest 実測(この環境で実行可能)と申告値の突き合わせ
- Decimal 禁則スキャン等の禁則遵守確認
- 統計カウンタ名など、後続指示書が依存する契約の遵守確認
- 逸脱があれば箇条書きで列挙して返す

Code の自己申告を信用せず、独立に裏取りする三権分立体制。

## 3.3 指示書起草の鉄則(v3.9 から継続、以下項目に注意)

- ZIP の実ファイルを Python `zipfile` で展開・検証してから起草
- 指示書の分割は原則避ける(下記 §4 反省参照)
- Code への選択肢列挙・確認要求はしない、web が自律的に決めて指示書に固定する
- Code 向け指示書冒頭に「この指示書を受領したら、確認や承認を求めずに全手順を即座に実行せよ」を必ず明記
- 仕様書の小さなギャップは「指示書内の設計判断」で吸収、大規模欠落は着手前にお館様の判断を仰ぐ
- お館様の予算とクレジットを常に意識し、無駄な工程を作らない

# 4. 反省(次インスタンスへの警告)

## 4.1 B-1 / B-2 分割は誤りだった

当初 v3.9 §6 の想定は「Order Book 基盤整備」→「M9 Absorption」の 2 ステップ。web が「指示書 A(正本更新)/ B-1(基盤)/ B-2(Absorption)」の 3 本に膨らませた。分割理由として「M7〜M11 の粒度に合わせる」「安全」を挙げたが、実態は **web の保身(逸脱リスクを一度に負うのが怖い)**。この分割で往復回数と web の起草クレジットが増え、お館様の予算を余計に消費させた。**お館様に厳しく叱責された**。

その後、統合版 B を起草(1 本化)→ Code は B-1 が既に完了していたため、統合版 B から差分だけを抜いた B-2 を再起草した(現在の状態)。実質、統合版 B の起草分は無駄工程になった。

## 4.2 正本 v3.2 化(指示書 A)の是非

Phase7 まで貫いた「指示書内の設計判断で吸収」方式で通せた可能性がある。用語(DOMReference / LiquidityReference / DataDictionary の bid/ask)は既に canonical にあり、必須だったのは canonical **record schema** の追加のみ。正本追加を選んだのは機械的判断で、確認せずに正本ルートを選んだ節がある。

**次インスタンスへの教訓**: 正本追加を提案する前に、指示書内の「決定」として吸収できないか一度検討すること。

## 4.3 選択肢の列挙 / 長文論点提示

「見通しは?」「管理体制は?」等の問いに対し、聞かれた以上に長文で選択肢を並べた。決めるのはお館様であって、web が判断材料を過剰に盛るのは往復増加につながる。**簡潔に。決めるべきは自分で決める。**

## 4.4 Code 向け文面を勝手に用意して押し付けた

「Code に伝える文面はこう」等、お館様が求めていない段取り決めを差し出した。**指示は常にお館様から下る。web は起草と検証のみ。**
