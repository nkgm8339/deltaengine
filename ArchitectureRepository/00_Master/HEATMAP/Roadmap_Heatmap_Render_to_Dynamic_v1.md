# 実行計画書: Bookmap相当ヒートマップ 描画〜動的化ロードマップ
**Version: 1.0 / 作成日: 2026-07-30 / 統制文書: HEATMAP_指示書_v1.6.md / 承認者: お館様**

---

## 0. 目的とお館様の要件

- 最終成果物: Bookmap相当の**動く**板情報ヒートマップ(時間を横軸に流し、各価格帯の指値厚みを
  色で塗り、板の濃淡が時間とともにスクロールする)。CVD等と重畳可能にする。
- お館様の要件(2026-07-30): 静的/動的の別は問わない。**速く・正確に・バグなく**作ること。
- 本書は個別指示書の親となるロードマップ。各Phaseの目的・成果物・「テストで固定する不変条件」を定める。
  個別Taskの実装詳細は各指示書(Instruction_*)に委ねる。

## 1. バグなく速く作るための基本戦略

1. **崩れやすい所を決定的入力で先に固める**。座標変換・時間スクロール・描画予算という
   動的で壊れやすい部分を、録画リプレイ(Phase 2-1の`sample_states`、同じ入力から同じ絵)で
   テスト可能にしてから作る。ライブ(二度と同じ入力が来ない)は最後に載せる。
2. **過去の失敗を再現テストで捕捉**。x座標-185.25pxバグ→座標変換の往復テスト。
   p95描画予算16ms超過→フレーム描画時間の計測とテスト化。
3. **描画核はLive/Replay共通**。DeltaEngineのReplay/Live二重構造に従い、描画ロジックは
   まずReplayで正しさを保証し、Phase 3でLiveへ載せ替える。新規リスクを接続層だけに閉じ込める。
4. **v1.6哲学の遵守**。数量はDecimal、`float()`禁止、bids/asksは別レイヤーで正規化・混合しない。

## 2. Phaseロードマップ

### Phase 2-2: 描画核(録画リプレイ入力、1枚出力で検証)
- 目的: 動的化前に、描画ロジックの核を決定的に固める。
- 成果物(すべて新規): `binner.py`(価格ビン集約・時間間引き)、`transform.py`(座標変換一元化)、
  `render_static.py`(色マッピング・1枚PNG出力・描画時間ログ)、各test、実データCLI。
- テストで固定する不変条件:
  - ビン境界・Decimal保持・間引き規則の決定性・ギャップ保持・**入力順序非依存**
  - 座標往復の恒等性・端点厳密一致・**負座標が出ないこと**(x座標バグの再発防止)
  - 出力寸法・ギャップ列の非塗り潰し
- 実行指示書: `Instruction_Phase2-2_Renderer_v1.1`(作成済み。Task 0承認済み、Task 1着手指示済み)。
- 位置づけ: 静的1枚はゴールではなく、動的の描画核をテストするための決定的検証環境。

### Phase 2-3: 動的化(録画駆動、ブラウザで動くヒートマップ)
- 目的: ライブ接続せずに「動くBookmap」を実現し、時間軸スクロールと描画予算を固める。
- 成果物(すべて新規): 直近N列のリングバッファ(価格×時間の窓を保持し新サンプルで左送り)、
  Canvas 2Dへの逐次描画更新、録画を時間順に供給するReplayドライバ、時間軸スクロールのテスト、
  フレーム描画予算テスト。
- テストで固定する不変条件:
  - リングバッファの列追加・古い列破棄でグリッド整合が保たれること(境界off-by-one検出)
  - スクロール後も価格軸・色スケールが一貫すること(サンプル列内で正規化しない=全体基準を維持)
  - **1フレーム描画時間の計測を必須化**し、p95予算(参考16ms)を計測・記録・テストで監視
  - GAP/SYNC_FAILED区間を流し込んでもスクロールが破綻せず、欠損が空白として流れること
- 保護対象(webapp/static/index.htmlの別系統Heatmap UI)に触れる必要が出たら停止・確認。
- 実行指示書: 本ロードマップ承認後に別途作成。

### Phase 3: ライブ載せ替え(WebSocket逐次描画)
- 目的: Phase 2-3で検証済みの描画核へライブストリームを接続。新規実装を接続層に限定。
- 成果物: ライブdepth→(既存同期state machine=DepthSyncCoordinator)→描画核への配線、
  接続断・再接続処理、Live/Replay切替。
- テストで固定する不変条件:
  - 描画核の入力契約がReplayと同一(同じサンプル型を渡す)であること
  - 再接続後のresyncが録画テストと同じ経路を通ること(未検証diffがbookへ入らない契約の維持)
- 実行指示書: Phase 2-3完了後に別途作成。

### Phase 4: 拡張(v1.6 §3 Phase 4に準拠)
- CVD重畳、約定バブル(記録に既存のtradeを使用)、大口指値ハイライト、8パターン参照カード連携。

## 3. スケジュール上の判断(統括)

- Phase 2-2は着手可能な状態(Task 0承認済み)。**このまま進めるのが最速**。作り直しは不要。
  静的1枚の検証は動的の描画核テストそのものであり、無駄にならない。
- 「動く見た目」が出るのはPhase 2-3。Phase 2-2の各Task(特に座標変換テスト)を通すことが、
  Phase 2-3でスクロールがバグらないための前提になる。順序を飛ばすと過去の座標バグを
  動的環境で踏み、切り分けが困難になる(速く作るために順序を守る)。
- したがって統括判断: **v1.6のPhase順を維持し、Phase 2-2を完走 → Phase 2-3で動的化**。
  この計画がお館様の「速く・正確に・バグなく」に最も適う。
