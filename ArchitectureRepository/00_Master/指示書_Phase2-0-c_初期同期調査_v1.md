## 0. 背景(Phase 2-0-b 確定事実)

Phase 2-0-b 報告(`ArchitectureRepository/00_Master/HEATMAP/Phase_2-0-b_記録物現物提出報告.md`)で以下が現物確定した。

- 両captureともsnapshot接続条件 `U <= u_snapshot + 1 <= u` が **FAIL**(§4.2)。
- 欠落規模: 第1セグメント 227ms / 約10,175 update ID、第2セグメント 193ms / 約14,300 update ID。
- 原因候補: 取得層がREST snapshot取得後にdepth streamの記録を開始しており、Binance標準手順(stream購読・バッファ開始 → REST snapshot → 接続条件を満たすdiffから適用)の順序になっていない。
- `OrderBookStateManager`(orderbook.py:97)のlenient受理(233-242行)はこの穴をライブ表示上は隠すが、記録の再構築では欠落窓で変化したlevelが誤った値のまま残り得る。

統括判断: 記録器/取得層の初期同期手順を是正し、snapshot接続PASSの記録を取れる状態にする。**本指示書は調査と計画提示のみ。実装・変更は禁止。**

## 3. タスクA: 現行初期同期手順の現物特定

以下をすべてファイル:行番号付きで報告する。

1. **INITIAL_BOOK_SYNC snapshotの生成箇所**: `_capture_reason: "INITIAL_BOOK_SYNC"` を付与してREST深度snapshotを取得・記録するコードの現物(ファイル、行番号、関数名、呼び出し順序)。
2. **depth stream購読の開始箇所**: `@depth` streamの購読とraw_recorderタップへの流し込みが始まるコードの現物。
3. **時系列の確定**: 1と2がどの順序で実行されるか。snapshot取得の開始から最初のdepthUpdateがrecorderに届くまでの経路を、コードの実行順で追って報告する。227ms/1万件超の欠落がどの区間で生じるかを、コード根拠で特定する。
4. **バッファの有無**: stream受信からrecorder書込までの間に、snapshot取得前のdiffを保持するバッファ機構が存在するか。存在するなら現物、存在しないならその旨。
5. **snapshot再取得(gap後)の経路**: ライブ運転中にgapが起きた場合、REST snapshotを取り直して記録に挿入する経路が存在するか。存在するなら現物、存在しないならその旨(Phase 2-0-bの記録にはINITIAL_BOOK_SYNC以外の`_capture_reason`が出現していない)。
6. **DepthHistoryRecorder側の受け口**: `src/acquisition/depth_history_recorder.py` がsnapshotとdiffを受け取るインターフェースの現物(メソッド名、行番号)。是正時にrecorder側の変更が必要か、取得層のみで済むかの判断材料とする。

## 4. タスクB: 是正計画の提示(実装しない)

タスクAの現物に基づき、以下の要件を満たす是正計画を提示する。変更対象ファイル・変更内容の概要・想定リスク・影響するテストを列挙する。コードは書かない(計画のみ)。

是正後に満たすべき要件:

1. depth diffの受信・バッファリングを**REST snapshot取得より先に**開始する。
2. REST snapshot取得後、バッファ内に `U <= u_snapshot + 1 <= u` を満たすdiffが存在することを確認してから記録セッションを確立する。満たさない場合はsnapshotを再取得する(上限回数付き。上限到達時はエラーを記録して明示的に失敗)。
3. 記録は引き続き**到着順・全量**(ADR-011)。バッファしていたsnapshot以前のdiffも破棄せず記録してよいが、その場合は再構築側が判別できる形にする(方式はタスクA-6の現物を見て提案)。
4. manifestに同期検証結果を追加する(例: `sync_verified: true/false`、検証に用いたsnapshot `u` と最初の有効diffの `U`/`u`)。
5. ADR-003(単一ループasyncio、スレッド禁止)、`float()`禁止、既存機能無劣化を維持する。
6. Replay/Liveパイプライン二重構造への影響有無を明記する。
7. 次回検証録画でrotation境界の実データを取得できるよう、`max_bytes` を録画時に小さく設定できる経路(config/環境変数)の現状を報告に含める(変更はしない)。
