## 1. 背景と現行問題

現行システムは、1分足を基準に、Flowだけを複数秒・複数分の観測窓で表示している。

そのため、FLOWを5mへ切り替えても、次は1分基準のままである。

- ローソク足
- CVD
- Delta
- Footprint
- Imbalance
- Absorption
- エントリー判定
- 事後結果

HFMのスプレッドにより1分運用が成立しにくいという観測がある。解決策は表示窓の変更ではなく、計測・判断・執行・事後評価を5分・10分へ移すことである。

## 3. ネイティブ時間軸の定義

### 3.1 RAW約定を唯一の入力源にする

5分・10分の全計算は、受理済みRAW約定列から直接行う。

1分足を束ねた値を、5分・10分の元データとして再利用しない。

時間境界はUTCで固定する。

### 3.2 5mプロファイル

- UTCの5分境界で約定を区切る
- 5分の約定からOHLCを作る
- 5分の約定からDeltaを作る
- 5分の約定からCVDを更新する
- 5分の約定からFootprintを作る
- 5分の約定からImbalance / Absorptionを判定する
- 5分足確定後にFlow状態を判定する
- 5分足確定後にだけエントリー候補を作る
- Outcomeを5分単位で保存する

### 3.3 10mプロファイル

5mプロファイルと同じ処理を、UTCの10分境界で行う。

10分足を1分足10本の見た目集約として扱わない。

## 4. 時間軸の分離

時間軸は次の3つを混ぜない。

### 4.1 計測時間軸

約定を集計する単位。

- 1m
- 5m
- 10m

### 4.2 判断時間軸

状態・トリガーを確定する足。

- 5mプロファイル: 5m足の確定
- 10mプロファイル: 10m足の確定

### 4.3 事後評価時間軸

5mプロファイルの例:

- 1本後 = 5分後
- 2本後 = 10分後
- 3本後 = 15分後
- 6本後 = 30分後

10mプロファイルの例:

- 1本後 = 10分後
- 2本後 = 20分後
- 3本後 = 30分後
- 6本後 = 60分後

1m・5m・10mのOutcomeを同じ標本へ入れない。

## 5. データ処理境界

```text
RAW TRADE
   ├─ 1m Observation Pipeline
   ├─ 5m Execution Pipeline
   └─ 10m Execution Pipeline
```

5m・10mは、それぞれ独立した状態を持つ。

```text
5m:
  Candle / CVD / Delta / Volume
  Footprint / Imbalance / Absorption
  Flow Price Response / Event / Outcome

10m:
  Candle / CVD / Delta / Volume
  Footprint / Imbalance / Absorption
  Flow Price Response / Event / Outcome
```

既存の`MultiTimeframeCandleAggregator`は補助的な高時間足ローソクを作る仕組みであり、5m・10mのExecution Pipelineそのものではない。表示用集計器へ機能を足すだけで完了にしない。

## 6. Flow Price Responseの時間軸別再計算

現行の`windows_sec`はローリング観測窓であり、実行時間軸とは別物である。

### 6.1 5m

- 5分足単位の圧力
- 5分足単位の価格反応
- 直近の5分足群による継続性
- 30〜60分を基準とした相対比較
- 5m専用のEFFECTIVE / STALLED / TRAPPED / UNCLEAR

### 6.2 10m

- 10分足単位の圧力
- 10分足単位の価格反応
- 直近の10分足群による継続性
- 60〜120分を基準とした相対比較
- 10m専用のEFFECTIVE / STALLED / TRAPPED / UNCLEAR

1分の`BUY_TRAPPED`を、5m・10mの状態として流用しない。

## 7. エントリー判定

### 7.1 5m

```text
5m状態発生
→ 5m足終値で価格トリガー確定
→ 次の5m足で執行
```

### 7.2 10m

```text
10m状態発生
→ 10m足終値で価格トリガー確定
→ 次の10m足で執行
```

形成中足（FORMING）ではエントリー判定しない。
