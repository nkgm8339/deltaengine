# DeltaEngine座学 第9講 — 事後成績とデータ品質

作成日: 2026-07-21  
対象: Flow状態と時間窓を理解した人  
テーマ: 「当たったように見える」を、検証できる記録へ変える

---

## この講義のゴール

1. EventとOutcomeの関係を説明できる
2. forward return、max up、max downを説明できる
3. 1/3/5/10分後を分ける理由が分かる
4. 重複標本と異常データを除外できる
5. 観測値から未検証の勝率を作らない姿勢を身につける

最も大切な一文はこれ。

> **未来を語る前に、いつ、どの状態が起き、何分後に、実際いくら動いたかを保存する。**

---

## 1. EventとOutcome

### Event

ある時間窓が新しい非UNCLEAR状態へ変化した瞬間の観測記録。

保存項目の例:

- 発生時刻
- 時間窓
- 状態
- 圧力側
- BUY/SELL数量
- 圧力比
- 継続率
- 始点・終点価格
- 価格変化bps
- 相対出来高
- 約定数

### Outcome

Event発生後の実際の値動き。

- 1分後
- 3分後
- 5分後
- 10分後

予測確率ではなく、生の事後結果を保存する。

---

## 2. Forward Return

```text
forward return bps
= (outcome price - observed price) / observed price × 10,000
```

例:

```text
発生時価格 = 100,000
3分後価格 = 100,050

forward return = +5bps
```

値は市場価格の上下で符号を付ける。
SELL_TRAPPEDだから自動で符号を反転するわけではない。

状態別に評価するときは、BUY/SELL方向の定義を分析側で明示する必要がある。

---

## 3. Max UpとMax Down

結果時点の価格だけでは、途中経路が分からない。

### max up bps

Event発生後から期限までに到達した最高価格の上昇幅。

### max down bps

Event発生後から期限までに到達した最低価格の下落幅。

例:

```text
発生時: 100,000
途中高値: 100,080  → max up +8bps
途中安値: 99,950   → max down -5bps
3分後: 100,020     → forward return +2bps
```

最終的には+2bpsでも、途中で-5bps逆行していたことが分かる。

---

## 4. なぜ4つの期限を見るのか

同じ現象でも寿命が異なる。

| 期限 | 見ること |
|---:|---|
| 1分 | 直後の反応 |
| 3分 | 短期の持続 |
| 5分 | 数本の足にまたがる反応 |
| 10分 | 効果が残るか、戻るか |

1分後に+5bpsでも10分後に0bpsなら、方向は合っても寿命が短い。
1分後は0bpsで10分後に+8bpsなら、反応開始に時間がかかった。

「方向」と「寿命」を分けて集計する。

---

## 5. まず分ける軸

最低でも次を混ぜずに集計する。

```text
state × window_sec × horizon_sec
```

例:

```text
BUY_STALLED × 30秒窓 × 1分後
BUY_STALLED × 3分窓 × 1分後
BUY_TRAPPED × 3分窓 × 10分後
SELL_TRAPPED × 3分窓 × 10分後
```

状態も時間窓も期限も違う行を一つの平均にすると、何が効いたか分からなくなる。

相対出来高帯、時間帯、ボラティリティ帯を後から分ける場合も、先に定義する。

---

## 6. 重複標本の問題

6つの時間窓は同じ約定を共有する。
また、同じ市場現象が30秒窓から1分、3分へ広がることがある。

これらを完全に独立した3件と数えると、標本数を水増しする。

対策の考え方:

- 同一時刻帯の複数窓を一つの現象群として印付けする
- 同じ状態の連続Snapshotではなく状態変化Eventを使う
- 集計単位をEvent、現象群、セッションのどれにするか明記する
- 訓練期間と検証期間を時間で分ける

数字が多いことより、独立性が説明できることが大切である。

---

## 7. データ品質境界

2026-07-21 18:30:41 JSTより前には、非正値約定が混入し得た修正前データがある。

主標本は、この時刻以降のクリーンなデータとする。

修正前データを使う場合の最低除外条件:

```text
first_price <= 0
last_price <= 0
abs(price_change_bps) > 100
```

さらに、修正前のmax up/max downは研究値として使わない。

古い行を削除しないのは、原因調査と監査証跡を残すためである。
「保存すること」と「研究へ採用すること」は別である。

---

## 8. 異常値が統計を壊す例

正常な5件:

```text
+2, +3, -1, +4, +2 bps
平均 = +2bps
```

ここへ価格0由来の異常値-10,000bpsが一つ入る。

```text
平均 = 約-1665bps
```

現実の5件の傾向が完全に消える。

平均を計算する前に、入力価格、異常幅、修正境界、欠損を監査する。

---

## 9. 平均だけに頼らない

確認候補:

- 標本数
- 中央値
- 平均値
- 四分位範囲
- プラス/マイナスの件数
- max up/max downの分布
- セッション別のばらつき
- 1/3/5/10分での変化

極端値の影響が大きいとき、平均と中央値が離れる。

勝率を出すなら、何を「成功」と呼ぶかを結果を見る前に定義する。

例:

```text
BUY_TRAPPEDを下落仮説として評価し、
3分後forward return < 0 を成功と定義する
```

定義を結果に合わせて変えると検証ではなくなる。

---

## 10. 観測と推論の境界

### 観測できる

> 3分窓BUY_TRAPPEDが40件あり、10分後リターン中央値は-2.1bpsだった。

### 条件付きで推論できる

> この期間の標本では、BUY_TRAPPED後に下方向へ偏った。

### まだ言えない

> BUY_TRAPPEDなら将来も必ず下がる。

期間、相場環境、データ品質、重複、手数料、スリッページが変われば結果も変わる。

## 12. よくある誤り

### 82イベントあるから標本82

複数窓や同一現象が含まれ、独立標本数は少ない可能性がある。

### 一番良かった期限だけ報告する

後から期限を選ぶと都合のよい結果になる。1/3/5/10分を併記する。

### 平均がプラスなら有効

外れ値、中央値、分布、標本数を確認する。

### 古い異常行を削除すればよい

監査証跡は保持し、採用条件で除外する。

### 事後成績を売買確率と呼ぶ

誤り。まず特定期間の観測結果であり、将来確率には追加検証が必要。

## 13. 確認問題と解答

1. forward returnとmax upの違いは。  
   **答え:** forward returnは期限到達時の価格差、max upは期限までの途中最高値による最大上昇幅。
2. 1分後と10分後を分ける理由は。  
   **答え:** 方向だけでなく効果の発生時期と寿命が異なるから。
3. 最低の集計分割軸は。  
   **答え:** state × window_sec × horizon_sec。
4. クリーンな主標本の開始時刻は。  
   **答え:** 2026-07-21 18:30:41 JST。
5. 古い異常行を削除しない理由は。  
   **答え:** 原因調査と監査証跡を保持しつつ、研究採用は別条件で管理するため。
