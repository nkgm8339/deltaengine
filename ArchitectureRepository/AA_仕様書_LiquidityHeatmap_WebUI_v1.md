# 1. 目的

既存のオーダーブック表示に対し、「見方の可読性」を高める新しいビュー群を追加する。従来の板は待機流動性の単一スナップショットを見せるにとどまり、壁が時間の中で生まれ・食われ・引かれる動的変化、および約定がどの価格帯に溜まったかを画面上で読み取れない。本仕様はこの空白を、3つのビュー（ヒートマップ・出来高プロファイル・板ヒストグラム）と、それらへの切替およびフローティング拡大表示によって埋めることを目的とする。

本ビュー群は新しい指標を生成するものではない。既存の実装済みデータ（板同期・フットプリント・CVD・約定）を、異なる形で可視化することにより、裁量判断の速度と、自動化に向けた「計算過程の可読性」を両立させる。

# 3. 既存資産との関係（再利用方針）

本仕様は既存の正本および実装を Single Source of Truth とし、再定義しない。各ビューは以下の既存データを参照のみで再利用する。

| ビュー | 参照する既存データ | 出所 |
|--------|-------------------|------|
| 板ヒストグラム | 現在の板（bids/asks、価格→数量） | `OrderBookSnapshot`（orderbook） |
| ヒートマップ | 板スナップショットの時系列 | 上記を時間方向にサンプリング（フロント側で保持） |
| ヒートマップ（約定線） | 約定価格 | TICK / CANDLE の close |
| 出来高プロファイル | 価格レベル別の約定出来高 | `FootprintBar.levels`（buy_volume + sell_volume） |
| 吸収マーカー（将来） | Absorption 検出イベント | 既存 absorption |

配信経路は既存の WebSocket（PushBroker、TICK/CANDLE、板は on_candle にバンドル）を用いる。新規メッセージタイプは追加しない。

# 4. 全体構成

## 4.1 定位置スロット

ダッシュボードの既存オーダーブック位置に「表示切替トグル」を設ける。トグルは2状態。

- `伝統板`: 従来の縦ラダー板（既存表示を維持）
- `3枚ビュー`: 本仕様の3ビューを同一価格軸で横に並べたもの

既存の伝統板は撤去せず、既定表示として残す。

## 4.2 3枚ビューの並び（価格軸共有）

3ビューは縦の価格軸を共有し、同一の価格行が水平に揃う。左から順に配置する。

```text
[ 価格軸 ] [   ヒートマップ   ] [ 出来高プロファイル ] [ 板ヒストグラム ]
             時間 × 価格            価格別・約定出来高       価格別・現在板厚
```

同一行を左→右に読むことで、「その価格に壁があったか（そして食われたか）」「その価格帯に約定が溜まっているか」「今どれだけ板厚が出ているか」を一度に読み取れる。

## 4.3 フローティング拡大

定位置スロットに拡大コントロールを設ける。押下でフローティング（オーバーレイ）が開き、大画面表示となる。閉じると定位置へ戻る。フローティングでは§6.3の面積配分に従う。

# 5. 各ビュー仕様

## 5.1 ヒートマップ（主役・唯一の2次元ビュー）

- 軸: 横 = 時間（左が過去、右が現在）、縦 = 価格
- セル値: その時刻・その価格帯における待機流動性の量（bid/ask 合算、または後述の色分け）
- セル色: 量に応じた連続色（薄 → 厚壁）。§10.2 のヒートランプに従う
- オーバーレイ: 約定価格の軌跡を1本の線で重ねる
- 意味: 縦に走る明るい帯 = 居座り続けた壁。右へ向かって色が薄れる = 食われた／引かれた跡。約定線が明るい帯に触れて横に停滞する箇所 = 吸収の候補
- 価格バケット: 価格軸を一定刻みで束ねる（刻み幅は §12 の要チューニング項目）
- 時間窓: 直近 N 分ぶんを保持しスクロール（N は §12 の要チューニング項目）

## 5.2 出来高プロファイル（1次元・約定の価格分布）

- 軸: 縦 = 価格（ヒートマップと共有）
- バー長: その価格帯に溜まった約定出来高（水平バー、左端から右へ伸長）
- 出所: `FootprintBar.levels` の各価格レベルの buy_volume + sell_volume を、対象窓にわたり累積
- POC: 出来高が最大の価格帯を強調表示（§10.2 の warn 色）。POC = Point of Control、最頻約定価格
- 累積範囲: セッション単位、または直近 N バー（範囲は §12 の要チューニング項目）

## 5.3 板ヒストグラム（1次元・現在の板厚）

- 軸: 縦 = 価格（ヒートマップと共有）
- バー長: その価格の現在の待機数量（水平バー）
- 色分け: ミッドより上（ask）= sell 色、ミッドより下（bid）= buy 色、ミッド行 = 中立
- 出所: `OrderBookSnapshot` の bids/asks（価格→数量）
- 位置づけ: 3枚ビューにおける「今この瞬間」の断面。ヒートマップの最右列と整合する

# 6. 切替・フローティング挙動

## 6.1 定位置トグルの状態遷移

| 現在状態 | 操作 | 遷移後 |
|----------|------|--------|
| 伝統板 | トグル「3枚ビュー」 | 3枚ビュー |
| 3枚ビュー | トグル「伝統板」 | 伝統板 |
| いずれか | 拡大コントロール | フローティング展開（定位置は背後に維持） |

## 6.2 フローティングの開閉

- 開: 拡大コントロール押下でオーバーレイ表示。ヒートマップの時間スクロール（動的更新）を開始する
- 閉: クローズ操作でオーバーレイを消し、更新ループを停止する
- フローティング中も定位置の状態は保持する

## 6.3 フローティングの面積配分（設計根拠つき）

フローティングではヒートマップを主役として横に大きく取り、出来高プロファイルと板ヒストグラムを同一価格軸で脇に細く添える。

根拠: ヒートマップのみが2次元（時間軸を持つ）であり、横方向の拡大が時間解像度の向上に直結する。長い時間窓が見えるほど「本物の壁か見せ板か」の判別が効く。出来高プロファイルと板ヒストグラムは1次元（価格軸のみ）であり、横方向拡大の情報的恩恵が小さい。ゆえに面積はヒートマップの時間軸に集中投下する。

## 6.4 多通貨の扱い（設計判断）

一通貨を深く見ることに全振りする。複数通貨の同時監視はソフトウェア側でグリッド化せず、端末分離で対応する。本仕様に多通貨レイアウトは含めない。

# 7. データソースと配線

## 7.1 データフロー（既存経路の再利用）

```text
Binance Futures
  ├ depth  → 正規化 → OrderBook（OrderBookSnapshot）─┐
  └ aggTrade → 正規化 → CVD → Footprint（FootprintBar）┤
                                                       ▼
                              WebApp / PushBroker（既存 TICK/CANDLE、板は on_candle にバンドル）
                                                       ▼
                                            ブラウザ（本ビュー群）
                                                       ├ 板ヒストグラム ← 最新 OrderBookSnapshot
                                                       ├ ヒートマップ   ← 板スナップショットを時系列にバッファ
                                                       ├ 出来高プロファイル ← FootprintBar を累積
                                                       └ 約定線 ← TICK/CANDLE close
```

## 7.2 バックエンド無変更の原則

既定として、本ビュー群はフロントエンドで完結させる。ヒートマップの時系列と出来高プロファイルの累積は、既に配信されているデータをブラウザ側で保持・集計する。これにより、depth を永続化しない既存方針を維持し、バックエンドおよびテスト数（現行 348 passed）への影響を回避する。

例外: 描画負荷または帯域が実測で問題化した場合に限り、バックエンド側の集計（例: サーバ側での出来高プロファイル累積、または板履歴の間引き配信）を後続の別仕様として検討する。本仕様のスコープ外とする。

# 8. データ構造（フロントエンド保持）

既存のバックエンド型（`OrderBookSnapshot` / `FootprintBar` / `Candle`）は再定義しない。フロントエンドが描画のために保持するバッファのみを定義する。

## 8.1 ヒートマップ・リングバッファ

- 価格バケット配列 × 時間列のリングバッファ（2次元）
- 各時間列は、あるサンプリング時刻の板厚（価格バケット別）を保持する
- 新しい列を右端に追加し、最古の列を破棄する（時間窓を一定に保つ）
- サンプリング周期は §12 の要チューニング項目

## 8.2 出来高プロファイル・アキュムレータ

- 価格バケット → 累積出来高のマップ
- バー確定（CANDLE）ごとに、対象 `FootprintBar.levels` を加算する
- 累積範囲（セッション／直近 N バー）に応じて古い寄与を減算またはリセットする

## 8.3 約定線バッファ

- 時間列に対応する約定価格（close）の配列。ヒートマップと同じ時間窓・同じ列数

---

# 9. 描画・パフォーマンス

- 描画方式: Canvas を基本とする（多数セルの一括描画に適する）
- ヒートマップは列追加のたびに再描画する。目標は滑らかなスクロール（実運用フレームレートは §12 で確定）
- リングバッファにより、描画コストを時間窓の固定サイズに抑える（履歴の無制限成長を防ぐ）
- 出来高プロファイル・板ヒストグラムは、それぞれ更新契機（CANDLE 確定、板更新）でのみ再描画する
- 同一価格軸の3ビューは、価格→ピクセルの変換関数を共有し、行の水平整合を保証する

---

# 10. 色・レイアウト・寸法

## 10.1 基本パレット（既存 DeltaEngine 準拠）

| 用途 | 色 |
|------|-----|
| 背景 | `#0A0D12` |
| パネル | `#11161F` |
| buy（bid 側） | `#00E676` |
| sell（ask 側） | `#FF4D4D` |
| 警告 / POC | `#FFC400` |

## 10.2 ヒートランプ（薄 → 厚壁）

薄い流動性から厚い壁へ、寒色 → 暖色の連続ランプとする。低 = 背景に近い暗色、高 = 暖色（黄〜赤）。約定線は前景色（明色の1本線）で重ねる。具体的な色停止点は実装時に本パレットと整合する範囲で確定する。

## 10.3 レイアウト原則

- 3ビューは価格軸を左端に一度だけ置き、右へヒートマップ・プロファイル・板の順に並べる
- 定位置では各ビューが圧縮されるため、可読性の要は行の水平整合とヒートマップの最小幅確保にある
- フローティングでは §6.3 に従いヒートマップを最大化する

# 11. Decimal 規律・エラー処理

## 11.1 Decimal 規律（既存方針の厳守）

- バックエンドからブラウザへの数値は Decimal を文字列で送出する（`float()` 禁止、Decimal → str）
- ブラウザ側では、ピクセル座標計算のためにのみ数値へ変換する。表示・保持する権威値は文字列を維持する
- 価格・数量・出来高の権威的比較は文字列／固定精度で行い、丸め由来の誤差を画面に出さない

## 11.2 エラー・欠損時の挙動

| 事象 | 挙動 |
|------|------|
| 板未同期（BOOK ≠ SYNCED） | ヒートマップ・板ヒストグラムは「未同期」を明示し、確定データのみ描画する |
| フットプリント欠損バー | 出来高プロファイルは当該バーを加算せず、既存累積を維持する |
| WebSocket 切断 | 既存の再接続挙動に従う。復帰まで最新確定状態を保持表示する |
| データ列の欠落 | 空列として扱い、履歴の時間整合を崩さない |

# 13. テスト要件

本ビュー群は既定でフロントエンド完結（§7.2）のため、pytest の対象は限定的である。

- バックエンドに新規集計を一切追加しない構成では、既存 348 passed は無影響であること（回帰確認）
- 万一 §7.2 の例外（サーバ側集計）を後続で採用する場合は、その集計関数に単体テストを付す（Decimal 演算・float 不使用を含む）
- フロントエンド描画は pytest 範囲外のため、手動検証チェックリストで確認する
  - 3ビューの価格行が水平に整合すること
  - トグルで伝統板 ↔ 3枚ビューが切り替わること
  - 拡大でフローティングが開き、ヒートマップが時間スクロールすること
  - `BOOK=SYNCED` / LIVE 接続下で BTCUSDT が正しく描画されること
  - 画面表示値に丸め由来のアーティファクトが出ないこと
